# 에이전트 작업 인수인계

사용자용 매뉴얼이 아니다. 다른 PC나 새 에이전트 세션이 현재 브랜치와 검증 경계를
잘못 해석하지 않도록 유지하는 작업 상태 문서다. AGENTS.md에 따라 브랜치 변경, 병합,
서버 PC 실행 요청 전에 반드시 읽는다.

**지금 유효한 것만 둔다.** 날짜별 작업 기록(무엇을 왜 바꿨는지, 접은 실험)은
[작업 기록 보관](../archive/handoff-history.md) 끝에 날짜 절로 붙이고, 여기에는 결과로
바뀐 "현재 기준"과 "실물 미검증 목록"만 고친다.

## 현재 기준

- 기준일: 2026-11-03
- 브랜치: 작업은 `develop`, `main`은 `develop`의 fast-forward만 받는다. 서버 PC의
  클론은 `main`을 `git pull`한다.
- 단계: 저장소 골격, 실행 로그(`ct_toolkit.log`), 환경 점검(`ct.bat selfcheck`), 입력·출력
  지정(`ct.bat io-apply --list` 확인, `--export`로 CT 테스트 데이터 CSV의 머리글을 고친 사본 쓰기, 원소·멤버 줄의
  기호 단위 지정)까지.
  `--export`는 서버 PC 견본에서 한 바퀴 돌았다. CT가 툴킷 사본으로 목록대로 테스트를 만들고, 그 테스트를
  [가로]로 다시 내보내 돌리면 바꿀 것이 0이다(2026-11-03 todo.md 11·16·17절). 툴킷은 가로 꼴만 읽고, 세로
  꼴이면 설정을 [가로]로 하라고 알린다. CT를 부르거나 CT가
  내보낸 파일을 직접 고치는 기능은 없다. 단위 테스트는 에이전트 PC의 Python 3.12·3.14에서
  통과했다. 3.8은 문법 검사만 했다.
- 에이전트 PC: CT와 서버 PC의 결과 폴더가 없다. 실행 증거는 서버 PC에서만 나온다.
- 서버 PC(2026-10-29 `ct.bat selfcheck`): Python 3.14.7, openpyxl 3.1.5, git 있음, 콘솔
  utf-8(한글 정상). CT CLI는 `CT_HOME` 아래 `csc.exe`만 있고 `UtCLI.exe`는 없다. PowerShell은
  그룹 정책으로 막혀 있다(2026-10-29 todo.md 4절 첫 실행). 명령을 창에 붙여 넣는 방식도 쓸 수
  없다고 사용자가 알렸다(2026-11-02). 요청은 `todo.bat` 더블클릭과 절 번호로 돌린다. 실제 작업의
  입력·출력 지정은 `io-apply.bat` 더블클릭으로 돌린다(목록과 내보낸 폴더를 창에 끌어다 놓음, 2026-11-03
  todo.md 15절에서 서버 PC 확인).
- 입력·출력 지정은 `.utest`(Java 직렬화 바이너리)에 담기고, [테스트 가져오기]는 CSV 머리글이
  아니라 `.utest`의 지정을 따른다. 다시 가져오면 덮어쓰지 않고 새 테스트가 생긴다(2026-11-02
  todo.md 4·8절). [테스트 데이터로 테스트 생성하기]는 CSV 머리글대로 지정한 새 테스트를 만든다(9절).
  그래서 툴킷은 CSV 머리글만 고치고, 사용자가 원래 테스트를 지운 뒤 CSV로 테스트를 만드는 흐름을
  사용자가 승인했고(2026-11-02) `--export`가 그렇게 구현됐다(`docs/design/io-designation.md` "사용 흐름").
- TC별 분기 결과는 CT 보고서(html·xls·xlsx, 테스트별 결과 보고서 포함)에 없다(2026-11-02 todo.md
  7절). GUI에서도 못 얻는다. 제어 흐름 그래프 [뷰 내용 내보내기]는 html에 싼 gif 그림이고, MC/DC
  진리표 복사는 조합별 참·거짓뿐 어느 케이스가 커버했는지는 색으로만 보인다(10절). TC별 결과는 CT
  밖에서 구해야 한다(툴킷 추정 또는 손으로 채우기, 사용자와 정하는 중).
- 서버 PC의 CT: 2025 (V3), 빌드 20251127(Help > About). 맞는 매뉴얼은 빌드 날짜로 보아
  2025.12판이다(추정). CT 동작 근거는 2025.12판을 먼저 본다.
- CT 기능 근거: 슈어소프트 CT 매뉴얼(manula.com). CLI 키는 3.6 매뉴얼의 CLI Setting,
  기능 목록은 2026.06 매뉴얼에서 확인했다. 2025.12판의 CLI.ini 섹션 목록과 `csc.exe`
  실행 방법은 2026.06판과 같다.
- CT CLI는 버전마다 프로그램이 다르다. 2023 이후는 설치 폴더 바로 아래 `csc.exe`
  (`csc.exe -e -w <워크스페이스> --ini -O <CLI.ini>`, 2026.06 매뉴얼 CI/CD·CLI 프로젝트 실행),
  3.x 이하는 `plugins\com.codescroll.ut*\bin\UtCLI.exe`(3.6 매뉴얼 CLI Execution)다.
- 다음 할 일: 로드맵 1번 [목록대로 입력·출력 지정하기](../design/io-designation.md). 설계는
  2026-10-29 승인. 파일 형식과 상관없는 1차([구현 계획](../design/io-designation-plan.md))는
  main에 있고 서버 PC에서 예제 목록으로 돌았다. CSV 사본을 쓰는 2차(`--export`,
  [구현 계획](../design/io-designation-plan-2.md))는 견본에서 한 바퀴 돌았다(11·16·17절). 견본은 함수 하나,
  목록 9줄뿐이다. 사용자의 실제 목록은 `a.b`, `v[0]`, `v[1].s`처럼 멤버·원소까지 적고(2026-11-03), 툴킷은 그런
  줄을 기호 단위로 지정한다(1차, [설계](../design/io-designation-members.md)). 2026-11-04 todo.md 22절 견본에서 CT는
  구조체 배열을 `dmy_recs[0].dmy_s` 꼴로 `[0]`만 가져왔고, 툴킷이 더한 원소·멤버 칸은 말없이 버렸다. 그래서 2차(칸
  더하기)는 만들지 않는다. `tools/case_check.py`(경우 목록 `examples/ct_sample/io_cases.example.xlsx`)는 실제 흐름(`y`
  뒤 `n`)대로 고쳤고, 그 확인을 22절로 한 번 더 받는다. 실제 프로젝트 적용은 사용자의 평소 작업으로 하고(README 순서, 사본으로 만든 뒤 다시
  내보내 `n`으로 바꿀 것 0인지까지), 문제가 있으면 화면 캡처로 받는다. TC별 분기 표의 출처(아래)는 사용자가 정할
  차례다. 나머지 후보는 [로드맵](../design/roadmap.md).
- CT [환경 설정] > [테스트] > [데이터 내보내기]의 출력 방향은 사용자가 정하고 [가로]로 둔다(사용자 2026-11-03).
  세로 꼴은 더 확인하지 않고 읽게 만들지도 않는다. 툴킷의 세로 알림(`E_EXPORT_VERTICAL`)은 잘못 [세로]로
  내보냈을 때를 위한 안전망으로만 남는다.
- CT [테스트 데이터로 테스트 생성하기]는 CSV 머리글에서 CT가 처음 보는 기호 칸(테스트에 없던 원소 `[2]`, 없는
  멤버)을 말없이 버리고 테스트는 만든다. 멤버 일부만 지정된 머리글(다른 멤버 칸을 뺀 것)은 그대로 받는다
  (2026-11-04 todo.md 22절). CT가 처음 테스트를 만들면 배열은 `[0]` 원소만 가져온다.
- CT 2025 [테스트 내보내기]의 입력·출력 지정은 `UNITTESTS\<테스트 이름>.csv`의 머리글 줄
  (`<input>`, `<expect>`, `<output>`, `<toutput>` 구역)에 담기고 `testInfo.export`는 바뀌지 않는다
  (2026-10-29 todo.md 2절). 같은 폴더의 `.utest`도 지정과 함께 바뀐다(2026-11-02 4절). 자세한
  것은 설계 문서의 "견본 결과".

| 브랜치 | 역할 |
| --- | --- |
| `main` | 서버 PC가 pull하는 배포 기준. `develop`의 fast-forward만 받는다 |
| `develop` | 작업 브랜치 |

## 실물 미검증 목록

정적 구현과 단위 테스트만 거친 것이다. 서버 PC 실행 결과가 나오면 해당 줄을 지우고
결과를 작업 기록에 남긴다.

- `ct.bat io-apply --export`는 서버 PC에서 견본(함수 하나, 목록 9줄, 바뀜 2, 해제 1)으로만 돌았다(2026-11-03
  todo.md 11·16·17절). 여러 함수, 여러 소스 파일, 같은 이름 static 함수, 값을 넣은 뒤 `n`으로 다시 돌리기는
  실제 프로젝트에서 처음 본다.
- 원소·멤버 줄의 기호 단위 판정은 견본(`dmy_calc`, `dmy_pick`)의 경우 목록 19줄로 봤다(2026-11-04 22절, 16줄 기대대로,
  `행 18` `CT에 없음`). `행 16`·`17`은 확인 도구가 케이스 정리 없이 돌려 `값 있음`이었다. 고친 확인 도구(`y` 뒤 `n`)로
  22절을 다시 받는다. 실제 프로젝트의 여러 함수·구조체 배열 목록은 처음 쓸 때 본다.
- 세로 꼴 CSV의 모양은 13절 `out\9`의 칸 수·줄 수로만 짐작했다. 칸 1개인 줄이 구역 표시라는 것도 추정이라,
  세로 알림이 실제 [세로] 파일에서 나오는지는 모른다. 출력 방향은 사용자가 [가로]로 정해 더 확인하지 않는다.
- 툴킷은 CT가 정렬해 쓴 구역이면 정렬을 지켜 새 기호를 그 자리에 넣고, 아니면 구역 끝에 머리글에 처음 나온
  순서로 붙인다. CT가 받은 것은 견본에서 지정이 바뀐 기호 둘과 해제한 기호 하나가 있는 사본뿐이다(11·16·17절).
  정렬되지 않은 구역에 붙인 경우는 실물로 넣어 보지 않았다.
- 이름을 바꾼 테스트의 함수·소스 파일 이름을 읽는 `.utest` 배치(Java 직렬화 문자열의 길이와 바이트)는
  견본 한 개의 모양과 지어낸 바이트로만 시험했다. 실제 `.utest`에서 같은 값이 나오는지 모른다.
- 케이스의 값 칸에 따옴표 두 개(`""`)만 있어도 값으로 센다. 견본의 값 없는 칸은 빈 문자열이었다.
  CT가 값 없는 칸에 `""`를 쓰는 경우가 있으면 "값 있음"으로 잘못 건너뛴다.
- `ct.bat io-apply --list`는 서버 PC에서 예제 목록으로만 돌았다(2026-10-29 todo.md 3절). 실제 목록은
  사용자가 Codebeamer에서 긁어 README "입력·출력 지정 목록 형식"대로 만들므로 따로 확인하지 않는다
  (사용자 결정 2026-11-03). 형식에 안 맞는 줄은 첫 실제 실행에서 `목록 오류`로 나온다.
- `ct.bat`, 콘솔 한글, CT CLI 탐색, 실행 로그 쓰기는 2026-10-29 서버 PC 환경 점검으로
  확인했다.
