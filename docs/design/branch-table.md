# TC별 분기 표 만들기

상태: 승인(2026-11-24).

## 왜

2026-11-20 사용자가 툴킷의 목표를 처음부터 다시 정했다. 지금까지의 작업이 입력·출력 지정, `.utest` 조사,
CLI가 뒤섞여 복잡해졌기 때문이다. 자동화할 일은 둘이다.

1. 원하는 변수 목록대로 입력·출력 지정하기
2. TC 스텝마다 어느 분기를 탔는지 정리하기

둘은 서로 독립이라 하나씩 한다. 이 문서는 2번이다. 1번은 이 일 뒤에 다시 본다.

분기 표는 검토자에게 내는 제출물이다. 그래서 한 칸도 틀리면 안 된다. CT는 TC별 분기 결과를 화면에만 보여 주고
파일로 내주지 않아, 지금은 사람이 화면을 보고 옮겨 적어야 한다.

## 결과물

사용자가 말하는 "TC 스텝"은 CT 테스트 뷰에서 테스트(TEST) 아래에 있는 테스트 케이스(CASE) 하나다(사용자 2026-11-20).
이 문서의 "TC"도 CT 테스트 케이스를 뜻한다. 테스트마다 파일 하나, 그 안에 케이스마다 한 덩이를 둔다.

케이스마다 함수 안의 분기를 소스에 나오는 차례대로 적고, 그 케이스에서의 결과를 붙인다(사용자 예시를 바탕으로 함).

```
<케이스 이름>
D1 [T]   if (condition)
D2 [F]   else if (condition)
D3 [T/F] for (...)
D4 [-]   case A:
```

| 표시 | 뜻 |
| --- | --- |
| `[T]` | 참으로만 지나감 |
| `[F]` | 거짓으로만 지나감 |
| `[T/F]` | 둘 다 지나감(반복문 안에서 여러 번 지난 경우 등) |
| `[-]` | 그 TC에서 닿지 않음 |
| `[?]` | CT 데이터에서 읽지 못함(실패로 센다) |

- 무엇을 분기로 세는지는 CT의 분기 커버리지를 그대로 따른다(`if`, `else if`, `switch`의 `case`·`default`, 반복문 등).
  툴킷이 따로 정하지 않는다. `case` 줄의 T·F가 무엇을 뜻하는지도 CT 데이터에서 본다.
- 조건 글자는 소스 줄에서 가져온다.
- 시험 대상 함수 안의 분기만 넣는다. 그 함수가 부르는 함수(같은 파일의 static 함수 등) 안의 분기는 넣지 않는다
  (사용자 2026-11-23).

## 목표, 하지 않을 것, 실패로 볼 것

**목표**

- CT가 실제로 잰 TC별 분기 결과를 그대로 옮긴 표. CT 화면(TC를 고른 소스 편집기의 참·거짓 표시)과 칸마다 같아야 한다.
- 서버 PC에서 더블클릭과 폴더 끌어다 놓기만으로 돈다.

**이번에 하지 않을 것**

- 입력·출력 지정(다음 일)
- MC/DC의 조건(`C0`, `C1`) 단위 결과
- 타깃(RTV) 실행 결과, 통합 테스트. Host 단위 테스트만 본다.
- 표 꾸미기(엑셀 양식 등). 글자 파일까지만 만든다.

**돌아가도 실패로 볼 것**

- 짐작한 칸. CT 데이터에 없는 칸을 툴킷이 소스나 입력값으로 추정해 채우면 안 된다. 못 읽은 칸은 `[?]`로 두고 화면에
  실패로 센다.
- 원본 소스, CT 프로젝트, 작업 공간을 고치는 것. 툴킷은 읽기만 한다. CT로 테스트를 다시 돌려야 한다면 작업 공간 사본에서만
  돌린다(아래 "방법"의 A').
- 화면에 고객 소스의 함수·파일·변수 이름, 조건 글자, 경로가 찍히는 것. 표 파일은 서버 PC에만 남는다.

## 제약

- 서버 PC: CT 2025 (V3) 빌드 20251127, 매뉴얼은 2025.12판. Python 3.14.7이지만 코드는 3.8 이상에서 돌게, 표준 라이브러리
  우선(AGENTS.md).
- 서버 PC는 PowerShell이 막혀 있고 명령을 붙여 넣을 수 없다. 확인은 `todo.bat` 더블클릭과 절 번호
  (`tools/todo_run.py`의 `SECTIONS`), 실제 작업은 `io-apply.bat`처럼 따로 둔 `.bat` 더블클릭으로 돈다.
- 화면은 한 장(120열 40줄 안쪽)에 개수와 정해 둔 문구만 찍는다. 긴 내용은 파일에 쓰고 이름만 찍는다.
- CT 안의 Java는 21.0.4이고 컴파일러가 없다. FST 2.45와 CT 모델 jar가 있다. 에이전트 PC에서 컴파일한 `.class`를
  커밋하는 길이 열려 있다(`tools/java/README.md`, 2026-11-04 todo.md 26절에서 `.utest`를 객체로 읽음).
- 에이전트 PC에는 CT가 없다. CT 데이터의 위치와 꼴은 서버 PC 확인으로만 안다.
- CT CLI(`csc.exe`, 2025.12 cli-project-execution)에는 커버리지나 TC별 결과를 내보내는 섹션·키가 없다.
- CT는 테스트 뷰에서 TC를 고르면 소스 편집기 왼쪽에 분기마다 "참만 / 거짓만 / 둘 다 / 안 지남" 표시를 그린다(2025.12
  coverage-view). 그래서 TC별 분기 결과는 CT 안 어딘가에 있다. [커버리지 내보내기]의 `.csd`는 프로젝트 전체를 합친
  커버리지다(2025.12 coverage-share). TC별 정보가 들었는지는 모른다.
- CT 보고서(html·xls·xlsx, 테스트별 결과 보고서)와 GUI 내보내기(제어 흐름 그래프, MC/DC 진리표 복사)에는 TC별 분기 결과가
  없다(2026-11-02 todo.md 7·10절).

## 방법

| 방법 | 내용 | 좋은 점 | 대가 |
| --- | --- | --- | --- |
| **A (고름)** | CT가 저장해 둔 TC별 커버리지 데이터를 찾아 읽는다 | CT가 직접 잰 값이라 CT 화면과 맞는다. 소스를 건드리지 않는다 | 위치와 꼴을 서버 PC에서 찾아야 하고, 끝내 못 풀 수도 있다. 읽기만 하므로 `.utest` 고쳐 쓰기보다 단순하다 |
| A' (데이터가 남지 않으면) | TC별 데이터가 실행 중에만 생겼다 사라지면, 툴킷이 작업 공간 사본에서 `csc.exe`의 `[ExecuteTest]`로 다시 돌리며 그 데이터를 잡는다 | 여전히 CT가 잰 값이다. 원본은 건드리지 않는다 | 사본 실행 시간이 든다. CT가 작업 공간을 쓰는 중이면 돌릴 수 없다 |
| B (A·A'가 막히면) | 분기마다 기록 코드를 심은 소스 사본을 CLI로 만든 별도 프로젝트에서 같은 테스트로 돌린다 | CT 내부 꼴에 기대지 않는다 | 고친 소스에서 나온 결과라 검토자가 문제 삼을 수 있다. 매크로 속 분기를 놓칠 수 있고 CT의 분기 번호와 맞추기 어렵다. Host만 된다 |
| C (뺌) | 툴킷이 CT 없이 함수를 직접 돌린다 | — | 스텁과 입력을 CT와 똑같이 재현할 수 없어 CT와 결과가 어긋난다 |

사용자가 A를 골랐다(2026-11-20). 서버 PC 확인 한두 번으로 데이터를 찾지 못하면 B로 넘어갈지 사용자에게 묻는다.

## 진행

### 1단계: 데이터 찾기(조사)

**견본.** 지어낸 소스(`examples/ct_sample/` 아래, `dmy_` 이름)에 함수 하나를 두고 `if`, `else if`, `else`, `switch`(`case`
여럿과 `default`), `for`, `while`, `? :`, `&&`가 든 조건을 넣는다. TC 몇 개로 분기마다 `[T]`, `[F]`, `[T/F]`, `[-]`가 모두 나오게
하고, TC마다 정답 표를 함께 둔다. 읽어 낸 데이터는 이 정답과 맞춰 본다.

**서버 PC 확인(todo.md 한 절).**

1. 사용자가 견본만 든 작업 공간(실제 프로젝트가 없는 곳)에 견본 프로젝트와 테스트를 만든다.
2. `todo.bat` 절이 작업 공간 폴더를 끌어다 놓게 하고, 파일 목록을 찍어 둔다.
3. "CT에서 테스트를 실행한 뒤 Enter"에서 멈춘다. 사용자가 실행하고 Enter를 누르면 다시 찍어 비교한다.
4. 새로 생기거나 바뀐 파일마다 확장자, 크기, 꼴(zip, XML, 글자, FST 머리, SQLite 등), 안에 견본 TC 이름이 들었는지를 찍는다.
   보는 곳은 작업 공간, CT 설치 폴더, `%TEMP%`, `%APPDATA%`, `%LOCALAPPDATA%`다(CT가 작업 공간 밖에 쓸 수도 있어서). 경로는
   `WS\…`, `CT\…`, `TEMP\…`처럼 각 뿌리 기준 상대 경로로 찍고, 견본 이름이 아닌 낱말은 `tools/java_probe.py`처럼 가린다.
   바뀐 파일이 많으면 견본 TC 이름이 든 것만 화면에 찍고 나머지는 개수와 파일로 둔다.
5. 같은 절에서 [커버리지 내보내기]로 만든 `.csd`도 끌어다 놓게 해 같은 것을 본다.
6. 사용자가 CT를 닫았다 다시 연 뒤 한 번 더 찍어, 찾은 파일이 남아 있는지 본다. 남지 않으면 A'로 간다.

사용자는 테스트를 CT 화면에서 실행한다(지금까지의 todo.md 절 모두). 견본도 화면에서 실행한다.

그다음 후보 파일을 꼴에 맞게 풀고(FST면 `tools/java`의 도우미처럼 CT의 Java로, XML·SQLite·zip이면 표준 라이브러리로),
견본 정답과 칸마다 맞는지 본다. 맞으면 1단계를 마친다.

### 2단계: 표 만들기

- 명령 `ct.bat branch-table`과 더블클릭용 `branch-table.bat`(`io-apply.bat`처럼 CT 프로젝트 폴더를 창에 끌어다 놓음).
- 테스트마다 글자 파일 하나를 `result\branch_table\<날짜시각>\` 아래에 쓰고, 그 안에 TC마다 한 덩이를 둔다.
- 화면: 테스트 수, TC 수, 분기 수, 못 읽은 칸 수와 그 이유(종류와 할 일).
- 마지막 실행 뒤 TC를 고쳐 결과가 낡았다는 것을 CT 데이터에서 알 수 있으면(CT는 그때 "테스트 실행 후 정보가
  변경되었습니다"를 띄운다, 2025.12 test-case), 그 TC의 칸은 `[?]`로 두고 다시 실행하라고 알린다.
- 실행 로그(`ct_toolkit.log`): 명령 시작·끝, 데이터 읽기 앞뒤, 실패하거나 일부만 된 경로와 이유.
- 마지막으로 사용자가 실제 함수 하나의 표를 CT 화면과 대조하는 확인 절을 받는다.

## 저장소를 어떻게 두나

- 서버 PC 실행 길(`todo.bat`, `tools/todo_run.py`, `ct.bat`, 실행 로그, `paths`, `selfcheck`)은 그대로 쓴다. 서버 PC에서 이미
  도는 유일한 길이다.
- 입력·출력 지정 코드(`io-apply`)와 `.utest` 조사 도구는 지우지 않고 둔다. 1번 일을 다시 볼 때 무엇을 남길지 정한다.
- todo.md 27절(`.utest` 조사)은 내린다. 지금까지의 결과는 `docs/ai/handoff.md`에 있다.
- 새 일은 새 모듈과 새 조사 도구로 하고 입력·출력 지정 코드와 섞지 않는다.

## 빌더에게 맡기는 것

- 견본 소스의 구체 모양과 TC 값, 정답 표의 꼴
- 조사 도구의 꼴 가리기, 가리기 방법, 화면 배치
- 2단계 읽기 코드(1단계에서 찾은 꼴에 따라)
- 조건 글자를 소스에서 뽑는 방법(CT 데이터에 줄·열이 있으면 그것을 쓴다)

## 사용자가 확인할 판단

내가 정했고 사용자가 아직 확인하지 않은 것이다.

- 그 TC에서 닿지 않은 분기도 빼지 않고 `[-]`로 둔다. 줄 수가 TC마다 같아 비교하기 쉽다.
- 번호는 사용자 예시대로 `D1`부터 소스 차례로 매긴다. CT의 MC/DC 뷰는 `D0`부터 센다.
- 결과는 테스트마다 글자 파일이다.
- Host 단위 테스트만 본다.
