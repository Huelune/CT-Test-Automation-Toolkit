# 원소·멤버 단위로 입력·출력 지정하기

상태: 사용자 승인(2026-11-04). 1차 정적 구현(기호 단위 맞춰 보기, `CT에 없음`)까지 했고 서버 PC 견본(todo.md
19·20절)은 아직이다. [목록대로 입력·출력 지정하기](io-designation.md)의 "나중"에 있던
"구조체 멤버 단위 지정"을 배열 원소까지 넓힌 것이다. 여기 없는 것은 상위 설계를 따른다.

## 왜

- 사용자의 실제 Codebeamer 목록은 변수를 멤버·원소까지 적는다. 예: `a.b`, `a.d`, `a.C`, `v[0]`, `v[1].s`
  (사용자 2026-11-03). 같은 배열이라도 `v[0]`, `v[2]`, `v[3]`의 `.A`만 출력인 식으로 원소·멤버마다 지정이
  다르다.
- 구현 전에는 툴킷이 변수 단위로만 지정했다. 이런 줄은 `변수 없음`으로 건너뛰고, 이름만 적은 줄이 없는 그
  구조체·배열(`a`, `v`)은 "목록에 없는 변수"로 보아 지정을 통째로 해제했다. 실제 목록에 쓸 수 없었고,
  그래서 todo.md 18절(실제 프로젝트 첫 적용)은 그런 함수를 빼고 돌리게 막아 두었다.
- CT는 테스트를 처음 만들 때 배열은 `[0]`만, 구조체 멤버도 일부만 넣어 둘 수 있다(사용자 2026-11-04, 견본
  2절의 `int dmy_hist[4]`도 머리글에 `dmy_hist[0]`만 있었다). 지금 사용자는 CT에서 원소·멤버를 손으로 늘려
  지정한다.

## 목표

- 목록 `변수` 칸에 멤버·원소까지 적은 줄은 그 기호만 지정한다.
- 목록에 줄이 있는 함수의 테스트에서, 어느 줄에도 걸리지 않는 기호는 지정을 해제한다.
- 목록이 가리키는 원소·멤버가 CT 머리글에 없으면, CT가 그런 칸을 받는다는 것이 견본으로 확인된 경우에만
  툴킷이 머리글에 칸을 더한다. 아니면 건너뛰고 개수를 센다(아래 "CT 머리글에 없는 기호").
- 지금의 변수 단위 목록(`a`, `dmy_ptr`, `return`)은 지금과 같게 돈다. 기존 단위 테스트가 그대로 통과한다.

## 하지 않는 것

- 소스를 읽어 멤버·원소가 실제로 있는지 확인하기. 툴킷은 소스를 모른다. 오타는 아래 "다시 돌려 확인"으로
  잡는다.
- 한 줄에 여러 원소 적기(`v[0..3].A`, `v[*].A`). 한 줄에 기호 하나다.

## 목록 규칙

사용자가 확인한 것(2026-11-03·04)과 내 결정을 나눠 적는다.

1. `변수` 칸에 소스 표기 그대로 `a.b`, `a.C`, `v[0]`, `v[1].s`처럼 적는다. (사용자)
2. 적힌 줄은 그 기호와 그 아래 기호를 지정한다. `v[0]`은 `v[0]`, `v[0].s`, `v[0].t`를 모두 덮는다. (사용자 확인)
3. 목록에 줄이 있는 함수의 테스트에서, 어느 줄에도 덮이지 않는 기호는 지정을 해제한다. 목록에 `a.b`, `a.d`,
   `a.C`만 있으면 `a.e`는 입력에서도 기대값에서도 뺀다. (사용자 답)
4. 이름만 적은 줄(`a`)은 지금처럼 그 변수의 모든 기호다. 한 기호를 덮는 줄이 여럿이면 가장 자세한 줄을
   따른다. `a` 입력과 `a.b` 출력이 같이 있으면 `a.b`는 출력, 나머지 `a` 멤버는 입력이다. (사용자 확인)
5. 대소문자를 구분한다(`a.C`와 `a.c`는 다르다). 앞뒤 공백은 지운다. (기존 규칙) 칸 안의 공백(`v[ 1 ] .s`)도
   지우고, 첨자의 앞 0은 뗀다(`v[01]` → `v[1]`, CT는 `[1]`로 쓴다). 이 밖의 꼴(`*p`, `(*p).x`)은 어느 기호와도
   맞지 않아 `변수 없음`이 된다. (내 결정)
6. 리턴은 `return`, 포인터 파라미터는 파라미터 이름(`p`)이다. `p` 줄은 `p`와 `p_mem`으로 시작하는 기호를
   덮는다. (기존 규칙) 포인터 파라미터가 가리키는 것의 멤버·원소를 따로 적는 줄은 목록에 없다(사용자 2026-11-04).
   그래서 `p->x` 같은 꼴은 받지 않는다.

목록 줄과 CT 기호의 대응:

| 목록 `변수` | 덮는 CT 기호 |
| --- | --- |
| `a` | `a`, `a.`로 시작하는 것, `a[`로 시작하는 것 |
| `a.b` | `a.b`, `a.b.`·`a.b[`로 시작하는 것 |
| `v[1].s` | `v[1].s`와 그 아래 |
| `return` | `returnVar` |
| `p`(포인터 파라미터) | `p_mem`과 그 아래(지금 규칙) |

"그 아래"는 기호가 줄의 글자 그대로이거나, 그 글자 바로 뒤에 `.`나 `[`가 이어지는 것이다. `a`는 `ab`를
덮지 않는다.

## 맞춰 보기

지금은 변수 하나에 지정 하나를 정하고 그 변수의 기호를 모두 같은 구역에 둔다. 앞으로는 기호마다 덮는
줄 가운데 가장 자세한 줄의 `구분`으로 구역을 정한다(`입력`은 `<input>`, `출력`은 `<expect>`·`<output>`·
`<toutput>`, `입출력`은 넷 다 — 지금과 같다). 지금 변수 단위로 하던 판단은 기호 단위로 옮긴다.

| 이유 | 언제 |
| --- | --- |
| 변수 없음 | 줄이 덮는 기호가 머리글에 하나도 없고, 아래 규칙으로 칸을 더할 수도 없다 |
| 목록 충돌 | 같은 함수에 글자가 같은 줄이 둘 이상인데 `구분`이 다르다. 자세함이 다른 줄은 충돌이 아니다 |
| 값 있음 | 줄이 덮는 기호 가운데 지정이 바뀌는 것에 값이 있다(`--reset-cases`면 안 건너뜀) |
| 타입 제외 | 줄이 덮는 기호에 툴킷이 꼴을 모르는 것이 있다 |
| CT에 없음 | 아래 "CT 머리글에 없는 기호"에서 칸을 더하지 않기로 된 경우 |

- **가장 자세한 줄**은 기호를 덮는 줄 가운데 (정규화한) 글자가 가장 긴 것이다. 덮는 관계라 글자가 길수록
  자세하다. 줄마다 자기가 가장 자세한 기호들이 그 줄의 "몫"이다. `a` 입력, `a.b` 출력이면 `a.b`와 그 아래는
  `a.b` 줄의 몫, 나머지 `a` 기호는 `a` 줄의 몫이다.
- 줄은 자기 몫을 통째로 하거나 통째로 건너뛴다. 건너뛴 줄의 몫은 원래 구역 그대로 두고 해제하지 않는다
  (지금 "이름 붙인 변수는 건너뛰어도 해제하지 않는다"의 기호판). 위아래 줄은 서로의 몫에 영향을 주지 않는다.
  `a` 줄이 `값 있음`으로 건너뛰어도 `a.b` 줄은 따로 판정한다.
- 줄이 덮는 기호가 머리글에 일부만 있으면(예: `v[1]` 줄에 `v[1].s`는 있고 `v[1].t`는 없음) 있는 것만 지정한다.
  툴킷은 `v[1].t`가 있어야 하는지 모른다. 덮는 기호가 하나도 없을 때만 아래 "CT 머리글에 없는 기호"로 간다.
- 해제는 어느 줄에도 덮이지 않는 기호다. 줄이 하나도 없는 변수는 모든 기호가 해제되므로 지금 동작과 같다.
  "값 있어 둠"(값이 든 기호는 `--reset-cases` 없이는 해제하지 않음)도 기호 단위다.
- 툴킷이 꼴을 모르는 기호(`supported` 거짓, 예 `p->x`)는 어느 줄에도 덮이지 않아도 해제하지 않는다. 같은 변수의
  아는 기호만 해제된다(변수 단위였을 때는 그런 변수를 통째로 두었다).
- 지금의 `mixed`(멤버마다 구역이 다른 변수)는 기호마다 따로 보므로 따로 다룰 것이 없어진다.

## CT 머리글에 없는 기호

CT가 처음 만든 테스트에는 배열 `[0]`만, 구조체 멤버도 일부만 있을 수 있다. 그래서 목록의 `v[2].A`가 머리글에
없는 일이 흔하다. 이때 툴킷이 할 일은 CT가 처음 보는 기호 칸을 [테스트 데이터로 테스트 생성하기]에서
받는지에 달렸다. 구현 전에 서버 PC 견본으로 본다(아래).

- **받으면:** 줄의 변수(첫 이름 `v`)가 머리글에 있을 때만, 줄이 가리키는 기호를 구분에 맞는 구역에 칸으로
  더한다(`입출력`이면 네 구역 모두, 지금 지정 규칙과 같다). 케이스 값은 빈 칸이다. CT도 값 없는 케이스를 빈
  칸으로 쓴다(상위 설계 견본 2절). 더할 수 있는 것은 더 쪼갤 것이 없는 기호다. `v[1]`처럼 원소 전체를 적었는데
  머리글에 `v[1]…`이 없으면, 같은 배열의 다른 원소(`v[0].s`, `v[0].t`)의 멤버 꼴을 빌려 `v[1].s`, `v[1].t`를
  더한다(내 결정). 빌릴 원소가 없으면 `CT에 없음`이다.
- **받지 않으면:** 그 줄을 `CT에 없음`으로 건너뛴다. `skipped.txt`에 "CT에서 원소·멤버를 늘린 뒤 다시
  내보내기"라고 적는다.
- 변수 자체가 머리글에 없으면 지금처럼 `변수 없음`이다. 칸을 더하지 않는다.

**다시 돌려 확인.** 툴킷은 소스를 모르므로 목록의 오타(`a.x`)도 칸으로 더할 수 있다. CT가 그런 칸을 말없이
버리면 조용히 틀린다. 그래서 README 순서에 "사본으로 테스트를 만든 뒤 다시 내보내 `n`으로 돌려 `바꾼 것 0`인지
본다"(todo.md 17·18절의 확인)를 넣는다. CT가 버린 기호는 그때 다시 `CT에 없음`이나 바뀜으로 나온다. 견본에서
CT가 없는 멤버를 어떻게 다루는지 보고, 알림을 내거나 테스트를 만들지 않으면 이 단계는 덜 중요해진다.

## 서버 PC 견본으로 먼저 볼 것

구현 전에 todo.md 절로 본다. 견본에 구조체 배열이 없어, 지어낸 소스 파일(`examples/ct_sample/` 아래
`*.example.c`)을 하나 더해 CT 견본 프로젝트에 넣는다. 기존 `dmy_calc`는 그대로 둔다.

1. CT가 처음 만든 테스트의 머리글에 구조체 배열이 어떤 기호로 오는지(`dmy_recs[0].dmy_s` 꼴인지), 원소와
   멤버는 몇 개 오는지.
2. 머리글에 없던 원소(`dmy_hist[2]`, 구조체 배열의 `[2]`의 멤버)를 기대값에 더한 CSV로 [테스트 데이터로 테스트
   생성하기]를 하면 그 원소가 지정되는지.
3. 없는 멤버를 더한 CSV를 넣으면 CT가 무엇을 하는지(알림, 무시, 테스트를 안 만듦).
4. 한 구조체의 멤버 일부만 기대값이고 나머지는 해제된 머리글을 받는지.

확인 화면에는 기호를 찍어야 1을 볼 수 있다. 견본 이름은 모두 지어낸 `dmy_`로 시작하므로, 확인 스크립트는
`dmy_`로 시작하는 기호만 찍고 나머지는 가린다. 2~4의 CSV는 사람이 고치지 않게 스크립트가 만든다.

## 구현 순서 (내 결정)

1. **견본 확인 절과 지어낸 소스.** 위 1~4를 todo.md 절로 요청한다.
2. **1차: 기호 단위 맞춰 보기.** 목록 규칙, 맞춰 보기, 해제를 기호 단위로 바꾼다. 머리글에 없는 기호를 가리키는
   줄은 `CT에 없음`으로 건너뛴다(칸을 더하지 않음). 견본 결과와 상관없이 맞는 동작이라 1과 함께 해도 된다.
   이것만으로도 사용자가 CT에서 원소·멤버를 늘려 둔 테스트에는 실제 목록을 쓸 수 있다.
3. **2차: 칸 더하기.** 견본 2·3에서 CT가 처음 보는 칸을 받는 것이 확인되면 위 "받으면"을 더한다. 받지 않으면
   만들지 않고 1차 그대로 둔다.

## 화면

- 지금 문구와 개수의 단위(줄 수, 해제·값 있어 둠은 변수 수)는 그대로 둔다. 기존 화면 단위 테스트가 그대로
  통과해야 한다. 멤버 하나만 해제돼도 그 변수를 해제 1로 센다.
- `건너뜀` 줄 끝에 `CT에 없음` 개수를 더한다.
- 2차에서 칸을 더했으면 `지정` 줄 끝에 더한 기호 수를 찍는다.
- 이름은 지금처럼 `skipped.txt`에만 쓴다. 해제·값 있어 둠은 `skipped.txt`에 기호 이름으로 쓴다. `secret` 이름으로
  화면·로그에 안 나오는지 단위 테스트로 본다.

## 구현자에게 맡기는 것

- 기호 덮기 판정과 자세함 비교를 어떻게 짤지. 지금 `io_match`와 `ct_export._new_header`가 변수 이름으로 쥐는
  것을 기호로 바꾸는 범위.
- 더한 칸을 구역 안 어디에 둘지. 지금 규칙(CT가 정렬한 구역이면 정렬 자리, 아니면 끝)을 따른다.
- 견본 확인 스크립트와 지어낸 소스의 모양.
